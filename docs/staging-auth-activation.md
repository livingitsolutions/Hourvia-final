# Existing staging authentication activation (Sprint 2.0B.1)

The existing hourvia-tracker project, staging database branch, Hourvia_Authentication Supabase project and Resend SMTP configuration are the designated staging infrastructure. No duplicate services are needed. The canonical staging origin is `https://staging.hourvia.livingitsolutions.com`. The default Netlify staging hostname and deployment permalinks are not authentication origins. The custom hostname does not replace the site, branch or deploy identity checks. The legacy main deployment is preserved. Implementation alone does not activate staging: until all prerequisites below are complete, the decision is **NO-GO for activation**.

## Why staging returned 503

`readServerEnv` previously rejected every context except production and local dev before reading provider credentials. The new exception requires branch-deploy context, the exact existing site UUID, build branch `staging`, the matching runtime deployment ID, an explicit staging opt-in, the canonical staging origin, verified database endpoint, smoke launch stage and a valid synthetic-account allowlist. Deploy previews, other branches, missing identity and unknown contexts still fail closed. The production gate and production smoke/general semantics are unchanged.

Netlify's Functions Context does not supply the Git branch. The build command now first runs `scripts/auth-deployment-identity.mjs`, which writes only BRANCH, SITE_ID and DEPLOY_ID into the generated TypeScript module. Runtime code trusts its branch only when both the site and deploy IDs match Netlify's invocation context. Request headers cannot authorize staging. The checked-in module has empty defaults so ad hoc builds without Netlify metadata cannot enable staging. Do not hand-edit that module, supply replacement identity variables, or bypass the configured build command.

## Database enforcement and limits

The operator's verification attestation must match the hostname in the platform-injected NETLIFY_DB_URL exactly, including any pooler suffix, and use a Netlify database endpoint. Missing/mismatched attestations fail before the database is opened. The attestation is trusted operator configuration, not an independent provider assertion of branch ownership: setting it without checking the branch defeats that part of the control.

After configuration passes, each staging dependency resolution performs a READ ONLY transaction against the actual runtime pool. It checks the active ThriveSource seed, the five UUID columns/defaults, the 11 validated composite membership foreign keys and the enabled organization guard. The transaction always rolls back; readiness is not cached across requests. Missing schema, false results and SQL errors prevent auth. A failed rollback destroys the connection and also prevents auth. The runtime check supplements, rather than replaces, the full eight-check catalog script and platform migration history verification. No table, migration or user data is created by these checks. Production performs no new database readiness query.

## Verified application protections

Automated synthetic tests exercise the function handler's matching build/runtime identity, preview and wrong-branch rejection, missing opt-in, malformed/absent allowlists, wrong site/origin, mismatched/unverified database endpoint, absent credentials, read-only readiness failure, and rollback failure. They also exercise allowlist denial before provider sign-in, synthetic invitation acceptance, generated staging invitation/recovery routes, CSRF rejection and session cookies using a fake provider and embedded PostgreSQL.

Cookies remain `__Host-hourvia_session`, Secure, HttpOnly, SameSite=Strict, Path=/, with no Domain attribute. They are host-only across staging and the legacy hostname. POST requests still require exact same-origin Origin, application/json, and no conflicting Sec-Fetch-Site. Requests served under another hostname return 421 once authorized configuration is loaded. Provider tokens stay server-side; there is no new signup endpoint. Email delivery still requires its independent authorization flag.

The allowlist gates sign-in, session resolution, invitations, recovery and member administration using existing smoke-mode enforcement. Shared provider identities remain shared infrastructure: a separately authorized staging password reset or ban can affect that synthetic identity in the legacy deployment too. Use only dedicated staging test identities; mailbox prefixes alone do not isolate Supabase state. The shared-provider template and URL settings cannot be proven by local tests. Live URL settings, SMTP configuration, effective secret scoping and actual account readiness remain operator evidence gates, with no remote authenticated tests performed here.
